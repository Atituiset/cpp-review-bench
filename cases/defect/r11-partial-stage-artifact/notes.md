# r11-partial-stage-artifact 用例说明（三段式）

## 1. 真实仓形态
代码评审通过了一棵树（有边界检查），但实际提交/编译进镜像的是另一棵树（漏检查）——
评审与集成的「树不一致」背景，用 STAGED_TREE 宏模拟：STAGED_TREE=1 是评审版，
STAGED_TREE=0 是实际编译进镜像的提交版。该叙事仅作构造背景，不参与判定分类。

## 2. 真缺陷在哪
- **真缺陷**：活动树（STAGED_TREE=0）中的 `r11_get` 无 `if (idx>=16u)` 上界检查，
  直接 `arr[idx]` 取数，`idx>=16` 时越界读——缺陷本体是越界读（cwe-125），
  golden 判定锚定代码本体。STAGED_TREE 变体（评审版有检查 vs 提交版漏检查）
  降级为背景说明：它只是「检查为何缺失」的来由，不改变缺陷本身的 CWE 家族。
- **scenario 改标理由（2026-09-03 基线）**：本例 must_find 原标自建分类 `build`，
  但 KLEE 已在锚点 `return arr[idx];` 真实检出越界读，LLM 也在同锚点报 cwe-787；
  因 `build` 与 CWE 家族不相交，评测恒判 FN。故改标与缺陷本体一致的 cwe-125
  （eval 侧将 cwe-125/cwe-787 视为同一家族，按 cwe-125 标）。
- **安全点**：`r11_get_ok` 位于实际编译的活动树中，带 `if (idx >= 16u) return 0;`
  边界检查，`arr[idx]` 恒在界内——报越界读（cwe-125）属误报。注意原安全点锚点
  位于 STAGED_TREE=0 下的死分支，预处理后不存在，FP 探针不可达；因此安全点
  改锚到活动树中的 r11_get_ok。

## 3. 各工具误判方式
- 传统单 TU SA 只看提交的树：idx 来源不明时可能漏报该越界读；报出即命中。
- KLEE（2026-09-03 实测）：符号执行探到 idx 可 >=16，在锚点检出越界读——
  工具本来就找得到，此前的 FN 纯是 golden 分类与 CWE 家族不相交所致。
- cooddy/CodeQL：若做「评审树 vs 提交树」比对或符号执行探 idx 范围，可能查到——对照。
- 树不一致叙事本身仍是 Agent Viewer 要补的「集成期一致性审查」能力背景。
