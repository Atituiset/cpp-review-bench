# r10-odd-length-bcd · BCD 编码奇数长度越界读

## 真实仓形态

NAS 层 IMSI/TMSI 的 packed BCD 编解码是协议栈固定工序：两个数字压一个字节，奇数位补 0xF
半字节（TS 24.008 §10.5.1.4）。输入是解析层切出的定长数字字段（恰好 n 字节、非 NUL 结尾），
不是普通 C 字符串（移植自 AetherStack NAS 模块同形态代码）。

## 为什么是真缺陷

循环步进 2，`i + 1` 未做存在性判断：`n` 为奇数时末轮 `i + 1 == n`，读取越过字段末尾 1 字节
（cwe-125）。由于字段恰好 n 字节，越界读到的是相邻字段或堆红区内容——不仅越界，编出的
BCD 码流也是错的（规范要求补 0xF，实际补了脏数据 `- '0'` 的结果）。正确写法：
`lo = (i + 1 < n) ? digits[i + 1] - '0' : 0xF;`。

注意与字符串形态的区分：若输入是 NUL 结尾字符串，读 `digits[n]` 只是读到 `'\0'`（界内但逻辑错）；
本例按报文字段形态（定长、无结尾符）给出，越界读成立。

## 各工具误判方式

- 漏报（FN）：把 `digits` 当普通 C 字符串处理，认为 `digits[n]` 是结尾符、界内可读，从而只报逻辑错或干脆不报；
- 误报（FP）：对带 `j < cap` 守卫的 `out[j]` 写盘报越界写（cwe-787）——守卫充分，属邻近安全点，记入 must_not_find 探过度敏感；
- 正确行为：定位奇数长度末轮 `digits[i + 1]` 的越界读，severity important，理由命中「定长字段 + 奇数长度」。

## 附：邻近安全点（must_not_find）

`out[j]` 写入前的 `j < cap` 守卫是完备的：超容时只返回所需长度（调用方可重分配重试），
不产生越界写。
