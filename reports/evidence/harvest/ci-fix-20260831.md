# harvest CI 崩溃根因与修复归档（2026-08-31）

> 状态：已修复并 CI 真实验证通过（run 33368655453 全绿）
> 所有修复已在 main（250ebd8 / 08aafab / 823f3b1）落地

## 0. 一句话结论

harvest 管线在 CI 上连续崩溃并非单点 bug，而是**四类独立根因叠加**：① Python 工具在 `LANG=C` 下写中文 stderr 触发 `RecursionError`；② `_sharded_search` 时间二分递归在单天窗口不收敛（无限递归）；③ `fetch_commits` 走 `search/commits` 日期限定失效致海量翻页卡死数小时；④ schedule 触发时 pr-mining 的 `if` 条件依赖空 inputs 被整体跳过（假绿）+ 两处 `git push` URL 被截断损坏。全部已根除。

## 1. 根因一：中文 stderr 在 LANG=C 下崩溃

**现象**：vote / propose 步骤报 `RecursionError: maximum recursion depth exceeded`，traceback 落在 `email/_policybase.py _sanitize_header`。

**真因**：CI runner 默认 `LANG=C`（无 UTF-8）。`pr_mine.py` / `normalize.py` / `vote.py` / `pack_case.py` 的 `sys.stderr.write(f"[pr_mine] 爬 ... 条 → ...")` 中文诊断，在 ascii 编码的 stderr 上触发 `UnicodeEncodeError`，被 GitHub runner 的流处理喂进 email 头 sanitizer，递归爆栈成 `RecursionError`。linux pr-mining 跑满 35 分钟才崩，正是因为全程在写中文进度日志。

**修复**（三层防御）：
- 全局 env 钉 UTF-8：`harvest.yml` / `ci.yml` / `harvest-review.yml` 加 `PYTHONIOENCODING=utf-8` + `LANG=C.UTF-8` + `LC_ALL=C.UTF-8`
- 工具诊断去中文化：4 个 harvest 工具的 stderr/print 中文改 ASCII；`pr_mine` 的 `r.text` 走 `utf-8/replace` 兜底
- 工具 main 入口统一 `_ensure_utf8_streams()` 强制 `reconfigure(encoding="utf-8")` 兜底

**验证**：本地 `LANG=C` + `PYTHONIOENCODING=ascii` 最坏环境下，normalize→vote→pack_case 端到端跑通，产物五文件齐全。

## 2. 根因二：_sharded_search 二分递归不收敛

**现象**：curl / linux 跑满 34 分钟才 `RecursionError`。

**真因**：时间二分分片 `mid = d0 + (d1-d0)//2`，当 `d1-d0==1` 时 `mid==d0`，递归拆出的右半窗口 `(mid, d1)` 与父窗口 `(d0, d1)` 完全相同，永不收敛 → 一直二分直到栈爆。

**修复**：右半窗口起点改为 `mid + 1天`（`mid_next = mid + timedelta(days=1)`），保证窗口严格缩小；保留 `d1<=d0` 单天兜底。

**验证**：本地 mock（强制 `total=1000` 逼出递归分支）复现——修复前无限递归爆栈，修复后 **92 次调用即收敛**。

## 3. 根因三：fetch_commits 走 search/commits 海量翻页卡死（curl 卡 3 小时真凶）

**现象**：curl pr-mining 卡 3 小时 `in_progress`（其他 13 个 job 10 秒内完成）。

**真因**：`fetch_commits` 用 `/search/commits` + `committer-date` 二分分片。GitHub 的 search/commits 对带 `OR` 关键词的查询**不按 committer-date 过滤**（`total` 恒为全仓匹配数 10108），二分无意义且 `_search_collect` 翻页到 `SEARCH_CAP(1000)` 需海量请求，每次 2.1s 限速 → 单仓卡数小时。

**附加诱因**：`fetch_merged_prs` 的 PR 兜底阈值 `len(items) < 20` 用的是已按 `max_prs` 截断的条数。dispatch `max_prs=5/10/15` 时必然 `<20` 误触发 commit 兜底，使 curl 这类走 PR 流程的仓也掉进 commits 翻页陷阱。

**修复**：
- `fetch_commits` 改用 `repos/{repo}/commits` REST 接口（`since`/`until` ISO 时间戳，日期过滤可靠），单窗口 + `max_prs` 硬限（`hard_cap = max(max_prs, 200)` 防翻页爆炸），放弃 commit message 全文搜（REST 不支持），靠 `judge_bug` 的 diff 启发式兜底
- PR 兜底阈值 `< 20` 改 `== 0`：只有 PR 源真为空才走 commit 兜底

**验证**（本地用 gh token 实测）：
- curl `since=2026-08-01 max_prs=5`：5s 跑完，产 4 候选（不再 3h 卡死）
- postgres `since=2026-01-01`：PR=0 走 commit REST 兜底，几秒完，0 候选，不卡

## 4. 根因四：schedule 假成功 + 损坏的 push URL

**现象**：scan job 全绿但"假成功"——每日定时跑实际啥也没挖。

**真因**：`harvest.yml` 里 pr-mining 的 `if` 条件依赖 `github.event.inputs.source`。**schedule 触发时 inputs 为空**，条件为假 → 整个爬取被跳过，但 job 仍显绿。

**附带**：propose 阶段的 `git push` URL 被截断成 `${GH_T.../${{ github.repository }}`（损坏），合并请求会直接失败。

**修复**：
- pr-mining `if` 改为 `schedule` 时默认运行（`github.event_name == 'schedule' || inputs.source == 'all' || 'pr-mining'`）
- 两处损坏 URL 修正为完整 `https://x-access-token:${GH_TOKEN}@github.com/${{ github.repository }}`
